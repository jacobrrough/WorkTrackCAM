### [ID-0089] — Python-first edit workflow for large files

After 22/23 confirmations (post-Cycle 39), the mitigation is no longer "retry `Edit`" or even "fall back to `Write`". The mitigation is: for files above ~800 lines, OR for any `.claude/` log file, OR for any file matching Rule 1's content-characteristic override (complex regex / Handlebars blocks / multi-byte UTF-8 separators / multi-line template interpolation — Cycle 35 escalation: this trigger now applies to the FIRST Edit attempt, not just the second), OR for any file already truncated once this session (regardless of which sandbox tool was used), skip the sandbox write-path tools entirely and use Python-via-bash (`python3 -c '...'` or a heredoc) to read the file, mutate it in memory, and write it back whole.

### [ID-0095] — splice-recovery marker-uniqueness

After `Edit` truncates, the recovery path is a Python splice that stitches the pre-truncation buffer onto the canonical tail from `git show HEAD:...`. Cycle 19 (bonus) lost **~47 test assertions** when the splice used `text.find('chamberTempC: profile.chamberT')` as its tail anchor — that string appeared twice in the file (first in the [ID-0070] bundled-profile block near line 200, then in the [ID-0079] M191 tail near line 810), and `find()` matched the FIRST. The splice deleted everything between the FIRST match and EOF. Rule: **never splice on a non-unique marker**.

## Rule 1 — Choose the write path up-front, not after truncation

Before touching any file, decide which tool is correct for that file:

| File size / type | Preferred tool | Why |
| --- | --- | --- |
| New file | `Write` | No existing content to damage |
| Existing file ≤ 500 lines | `Edit` | Cheap, diff-visible, truncation rate acceptable below this threshold |
| Existing file 500–800 lines | `Edit` with verification (see Rule 3) | Truncation observed but recoverable |
| Existing file > 800 lines | **Python-via-bash** (`p.write_text(...)`) | `Edit` truncation rate here is effectively 100% — do not use it |
| Any `.claude/` log (any size) | **Python-via-bash** append | Log files grow unbounded; always use the append pattern below |
| Any Handlebars post template (any size) | Python-via-bash OR `Edit` with a G-code fixture snapshot diff in the same cycle | G-code is sacred — see CLAUDE.md Safety Rule 1 |

### Python-via-bash patterns

**Full-file rewrite** (safest for large files):

```bash
python3 <<'PY'
from pathlib import Path
p = Path('src/shared/gcode-temp-validator.test.ts')
txt = p.read_text()
# ...mutate `txt` via string replace / regex / full reconstruction...
p.write_text(txt)
PY
```

**Targeted replace with uniqueness guard** (required — see Rule 2):

```bash
python3 <<'PY'
from pathlib import Path
p = Path('path/to/file.ts')
txt = p.read_text()
old = "exact unique string from file"
assert txt.count(old) == 1, f"marker not unique: {txt.count(old)} hits"
txt = txt.replace(old, "new text", 1)
p.write_text(txt)
PY
```

**Append (log files)**:

```bash
python3 <<'PY'
from pathlib import Path
p = Path('.claude/improvement-log.md')
entry = """\n---\n\n## Cycle N ...\n"""
with p.open('a', encoding='utf-8') as fh:
    fh.write(entry)
PY
```

## Rule 2 — Splice-recovery marker-uniqueness checklist

When an `Edit` truncates and you must stitch the pre-edit buffer onto the canonical tail from `git show HEAD:...`, every marker used to locate the splice point MUST pass ALL of the following checks BEFORE the splice is applied:

- [ ] `txt.count(marker) == 1` — the marker is unique in the file. If not unique, STOP and pick a different marker or switch to line-index splicing.
- [ ] **Cycle 61 escalation (count==0 escape-semantics, [ID-0095-data-v2]):** if the gate fails with `count == 0` (marker not found at all), check whether the marker contains a backslash escape (e.g. `\u2014`, `\n`, `\t`). Python's regular triple-quoted string parses `\u2014` as the em-dash byte `—`, but the on-disk file may contain the LITERAL six-character escape sequence `\u2014` (when the source is a TypeScript template literal with the JS escape, not a UTF-8 em-dash). Switch the marker to a Python raw string (`r"..."`) so the backslash is preserved literally. Cycle 61 [ID-0152] hit this on a `ShopApp.tsx` button-JSX marker; recovery cost was a single re-run of the script. The count==0 case is conceptually distinct from count==2 (anchor too short) -- count==2 means the marker is ambiguous, count==0 means the marker is wrong (escape semantics inverted across the Python<->TypeScript boundary).
- [ ] The marker spans at least one full line of meaningful code (not a fragment mid-expression). Fragment markers match too eagerly across unrelated contexts.
- [ ] The marker is byte-identical between HEAD and the pre-edit working-tree buffer. Run `git show HEAD:path | grep -n 'marker'` AND `grep -n 'marker' path` — both must land on the same line number or the shared-tail boundary has drifted and a splice is unsafe.
- [ ] If the damaged file contains two or more `describe(...)` or `function ...` blocks that reference the same fixture field name, assume the marker is ambiguous until proven otherwise with `txt.count(marker)`. This is the exact failure mode that bit Cycle 19 (bonus).
- [ ] For files > 500 lines with repeated fixture shapes, **prefer full-file reconstruction from a staged buffer** (`p.write_text(staged_buffer)`) over any splice. A splice is only safe when the marker is provably unique.
- [ ] If a splice must be used, prefer `text.rfind(marker)` (last occurrence) over `text.find(marker)` (first occurrence) when the shared tail is at the end of the file. `rfind` is the correct default when the lost region was the tail.
- [ ] Better: use a line-index splice — `lines = txt.splitlines(keepends=True); new = lines[:pre_trunc_idx] + head_lines[shared_tail_idx:]`. Line indices are unambiguous; `find` / `rfind` on long strings are not.

If ANY check fails, do not splice. Reconstruct the file from a staged buffer in a single `write_text`, or revert to HEAD and retry the edit via Python-via-bash.

## Rule 3 — Post-edit verification checklist

After every large-file edit (regardless of whether `Edit` or Python-via-bash was used), verify the write landed intact BEFORE moving on:

- [ ] `wc -l path/to/file` — total line count matches expectation (within ±2 of the delta you intended).
- [ ] `grep -c '^export ' path/to/file.ts` or equivalent landmark grep — count of top-level declarations unchanged (or changed by the intended delta).
- [ ] For test files: `grep -c '^  it(\|^  describe(' path/to/file.test.ts` — test/describe count matches the intended delta. **A silent drop of 47 `it()` blocks shows up here immediately.**
- [ ] For `.ts`/`.tsx`: `npx tsc --noEmit` (or the relevant focused `npm run typecheck`) passes at exit 0.
- [ ] For test files: `npx vitest run path/to/file.test.ts` passes at the expected count. Skipping this step hides truncation until the next full-suite run.
- [ ] For Handlebars post templates: the G-code snapshot test for the affected machine passes. **G-code is sacred — do not defer this check.**

If any check fails, treat the file as damaged and revert to HEAD (`git checkout HEAD -- path/to/file`) before attempting a second edit.
